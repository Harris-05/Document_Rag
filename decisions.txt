DECISIONS
=========

A running record of the design decisions behind Marginalia, why each was made, what was
rejected, and what it costs. Newest decisions are at the bottom. The README summarises them;
this file is the full reasoning.

Guiding principle: in contract analysis a wrong answer is far worse than a slow one. Where
accuracy and speed conflict, accuracy wins, and every answer must be checkable by the reader.


D1. Backend/frontend split: FastAPI + Next.js
---------------------------------------------
Decision: Python (FastAPI) owns ingestion, retrieval, the LLM loop and verification. Next.js
(React, TypeScript) is a thin client.
Why: the document and retrieval tooling (pypdf, LangChain loaders, BM25, numpy) lives in Python,
and keeping all logic in one service means quote verification cannot be bypassed by the client.
Cost: two deployables instead of one.


D2. Text extraction: LangChain PyPDFLoader / Docx2txtLoader, page by page
-------------------------------------------------------------------------
Decision: PDFs are read one page at a time with PyPDFLoader.lazy_load(); DOCX with Docx2txtLoader.
Why: page-at-a-time reading gives real progress ("page 34 of 150") and keeps page numbers, which
citations need later. The real file type is checked from the bytes, not the filename.
Known limit: langchain-community is in maintenance mode (it prints a sunset warning). The loader
usage is isolated in extraction.py so it can be swapped for pypdf directly without touching the rest.


D3. Uploads are processed in a background job and the UI polls
--------------------------------------------------------------
Decision: POST /documents returns 202 immediately; a background task extracts text and updates
progress in SQLite; the client polls the document every ~350 ms.
Why: survives page refreshes (the library shows in-flight documents), and a server restart marks
orphaned jobs as failed instead of leaving them "processing" forever. Simpler and more robust than
holding one long streaming request open.
Rejected: streaming the upload response (loses state on refresh); websockets (more moving parts).


D4. Documents with no readable text are rejected, not stored
------------------------------------------------------------
Decision: if the extracted text has fewer than MIN_TEXT_CHARS meaningful characters the document is
marked failed with a specific message ("probably a scan"), the stored file is deleted, and it never
appears in the library. A PDF where only SOME pages are empty is accepted but flagged with the
number of unreadable pages.
Why: saving an empty document and calling it a success is the exact failure the brief warns about,
and partly-scanned contracts must not silently look fully searchable.


D5. SQLite for persistence
--------------------------
Decision: one SQLite file (WAL mode) for documents, pages, chunks and chat messages.
Why: zero-ops, transactional, enough for a single-user tool. Page text is stored per page so
citations can point at a page and character range.
Cost: not horizontally scalable; swap for Postgres if multi-user is ever needed.


D6. Chat uses AGENTIC (corrective) RAG, not single-shot retrieval
-----------------------------------------------------------------
Decision: each question runs a loop, with accuracy prioritised over latency:

  1. QUERY GENERATION  The LLM rewrites the user's question (using recent conversation) into 1-3
                       search queries phrased the way contract text is phrased. It also flags
                       off-topic messages so they are never "answered from the document".
  2. RETRIEVAL         Hybrid search over every chunk of the document: BM25 (exact legal terms,
                       numbers, defined terms) plus embeddings (paraphrase and synonyms), merged
                       with Reciprocal Rank Fusion.
  3. QUALITY GRADING   The LLM acts as a strict judge. Each retrieved passage is scored
                       0 (irrelevant) / 1 (related) / 2 (directly answers), and the judge states
                       whether the relevant passages together are SUFFICIENT to answer, and if
                       not, what is missing.
  4. CORRECT           If retrieval is not sufficient and rounds remain (default cap: 3), the LLM
                       writes NEW queries targeting what was missing, and we retrieve again.
                       Relevant passages accumulate across rounds.
  5. AUGMENT           Only passages the judge accepted are placed in the answer prompt.
                       Irrelevant text never reaches the generator.
  6. GENERATE          The answer is streamed with numbered citations plus verbatim quotes.
  7. VERIFY            Every quote is located in the real document text by our own code
                       (see D8). Unfound quotes are shown as UNVERIFIED, never as genuine.

Why: legal questions are often phrased differently from the clause that answers them ("can they
walk away?" vs "termination for convenience"), so one retrieval pass misses. Grading before
generating means the model is not asked to answer from weak evidence, which is the main source of
confident wrong answers. Extra LLM calls cost seconds, which is acceptable here.
Rejected:
  - Plain top-k RAG: fast, but silently answers from whatever it happened to retrieve.
  - Stuffing the whole document into the prompt: does not fit for long contracts, and long-context
    models still miss clauses in the middle.
  - LangGraph for the loop: a hand-written async loop was chosen because streaming progress
    events, client cancellation and unit-testing with a scripted fake LLM are all simpler when the
    control flow is plain Python. The loop is small enough to read top to bottom.


D7. When retrieval never becomes good enough, the app says so
-------------------------------------------------------------
Decision: if the judge still finds no sufficient evidence after the round cap, the answer is a fixed
template (no LLM call), not generated prose. It states what was searched, and phrases the result as
"no passage was found" rather than "the contract does not contain". If the evidence is only partly
relevant, the answer is generated with an instruction to state what the document does not cover,
and the interface labels it "Partial evidence".
Why: a retrieval system can only prove it searched, not that something is absent. The brief calls
a confident "that clause does not exist" the worst possible output. Pages with no readable text are
reported alongside, because they were not searchable.


D8. Quote verification is done by our code, tolerant of extraction noise
------------------------------------------------------------------------
Decision: the model's quotes are never trusted, and neither are any page or position it reports.
Each quote is searched for in the stored document text after normalising BOTH sides:
  - whitespace runs (including newlines) collapse to one space
  - curly quotes/apostrophes and the various dashes map to plain ASCII
  - Unicode compatibility forms (ligatures such as "fi", non-breaking spaces) are folded
  - case is ignored
  - a second pass also repairs words hyphenated across a line break ("indem-\nnify")
  - an ellipsis inside a quote splits it into segments that must each appear, in order
Matching runs over the whole document joined across pages, so a quote that crosses a page break is
found. Matches are mapped back to ORIGINAL character offsets, which is what makes highlighting
possible. If a quote occurs more than once, the occurrence on the page the model cited is
preferred, and the count is reported.
Where it can still fail: a quote that rewords even one word is (correctly) rejected; text that
extraction itself garbles (tables, multi-column layout read out of order) may cause genuine quotes
to fail; scanned pages have no text to verify against; very short quotes (< 8 characters) are not
accepted as proof because they match almost anywhere.


D9. The index is built on first use, not at upload
--------------------------------------------------
Decision: chunking and embedding happen the first time a document is queried and are then cached
in SQLite. Chunks never cross a page boundary, so every chunk has an exact page.
Why: upload stays fast and keeps working without an AI key; a failed embedding call degrades the
search to keyword-only (and says so in the trace) instead of failing the document.
Cost: the first question on a large document pays the indexing time.


D10. Provider-agnostic LLM layer with an injectable client
----------------------------------------------------------
Decision: the agent talks to a small LLMClient interface (JSON completion, streamed completion,
embeddings). The OpenAI-compatible implementation reads key, base URL and model names from
environment variables. Tests inject a scripted fake.
Why: lets the whole retrieval-grade-correct loop be tested deterministically without network calls
or cost, and keeps the provider swappable.
Structured output uses JSON mode plus Pydantic validation (works across OpenAI-compatible
providers) instead of provider-specific schema features.


D11. Streaming, stopping, and history
-------------------------------------
Decision: POST /documents/{id}/chat streams Server-Sent-Event style frames: "step" (what the agent
is doing), "token" (answer text), "citations", "done", "error". Closing the connection stops the
run; whatever was generated is saved with status "stopped". One conversation thread per document,
stored in SQLite and reloaded when the document is reopened.
Why: the brief asks for visible progress rather than a spinner, and for partial answers to be
kept when the user stops.


D12. Short-term memory: a configurable window plus follow-up resolution
-----------------------------------------------------------------------
Decision: the last CHAT_MEMORY_TURNS question/answer exchanges (default 6, 0 disables, max 20) are
shown to the model, with earlier answers cut to CHAT_MEMORY_CHARS characters. The first agent step
also rewrites the user's latest message into a STANDALONE question ("What does it cover?" becomes
"What losses does the Supplier's indemnity cover?"). That resolved question, not the raw follow-up,
is what the relevance judge and the answer step receive. The user's own wording is still passed to
the answer step so nothing they said is lost.
Why: passing history only to the query step is not enough. A judge that sees "what does it cover?"
cannot tell which passages are relevant, so follow-ups would be graded and answered blind.
Only COMPLETED answers are remembered. A stopped or failed answer is partial or wrong, and feeding
it back as context would let it leak into later answers.
Cost: one more field in the first LLM call (no extra call). Memory is bounded, so cost per question
does not grow with conversation length. If the rewrite is empty or missing, the original wording is
used, so memory failures degrade to the previous behaviour rather than breaking the question.
Known limit: the rewrite is made by the model, so a badly ambiguous follow-up can be resolved
wrongly. The resolved question is not currently shown in the interface.


D13. Perceived latency: stream everything, hide what can be hidden, keep the accuracy steps
-----------------------------------------------------------------------------------------
Measured on a 150-page document, the answer text already streamed token by token. The waits were
elsewhere, so the fixes target those:
  - Before the first token: the plan, search, judge (and any refine) calls run one after another.
    This is the cost of D6 and is kept on purpose. Two things were overlapped: loading or building
    the search index now runs WHILE the model plans the queries (it hid most of the one-off embedding
    time on a first question), and the judge is asked to list only the relevant passages instead of
    scoring all of them, which shortens its output and so its time.
  - After the last answer token: the model writes the quotes list, then the quotes are verified.
    Nothing visibly changed during this phase, so the answer looked stuck. It now reports
    "Collecting the quotes that support the answer", and verification costs about 30 ms because the
    document text is normalised in a background thread from the start of the request.
  - Uneven delivery: providers often send text in bursts. The interface reveals streamed text at a
    steady pace that speeds up with the backlog, so it never lags the stream by more than a moment.
    People who prefer reduced motion see text as it arrives.
What was deliberately NOT done: skipping the judge, answering before retrieval is graded, or
showing an unverified answer first and correcting it later. Those would feel faster and would
undercut the accuracy guarantee. If time to first token still matters, the next option is a smaller,
faster model for the planning and judging calls only, behind its own setting.


D14. Better recall on plain clauses, and explanations that go beyond the quoted text
------------------------------------------------------------------------------------
Problems found: easy clauses (governing law, notices, termination) were being missed, answers could
only echo the evidence, and every model call was fixed at a very low temperature.

Retrieval changes (why easy clauses were missed):
  - Keyword search now stems words and drops filler words, so "terminate" matches "termination" and
    "terminated". Very short words are not stemmed, because stemming turns "AED" into "a".
  - Each chunk carries the section heading it sits under ("12. Termination"), found by a heading
    detector that rejects ordinary sentences. The heading is searched and embedded with the chunk, so
    a clause is found by its title even when its own wording never uses the title's words.
  - The user's whole question is searched alongside the planner's queries, and the planner writes up
    to 4 deliberately different queries (formal wording, section-heading wording, synonyms).
  - BM25Okapi was replaced by BM25Plus. Okapi gives a term zero weight when it appears in half the
    chunks, which silently broke keyword search on short contracts. A document smaller than the
    candidate window is now handed to the judge whole.
  - 14 passages are judged per round (was 10) and up to 10 can be used (was 8).
  - The judge was told to be "strict" and to reject anything that did not fully answer. It is now
    asked to be fair: short standard clauses count as direct answers, a section heading counts as
    evidence of relevance, and "sufficient" means the substance is covered, not every detail.
  - The chunks on either side of each strongly relevant passage are added to the answer prompt,
    marked as context, so a clause that runs across a chunk boundary is read whole.

Explanation beyond the context:
  The answer now has two clearly separated parts. FACTS ABOUT THE CONTRACT still come only from the
  evidence and still need a citation and a verified quote. After them the model may add a short
  "General explanation (not from the document)" using general legal knowledge: what a term means,
  why a clause matters in practice. It carries no citations, may not assert anything about this
  contract, and is shown in a separate callout so it cannot be mistaken for document content.
  This replaces the earlier rule that forbade any outside knowledge. The accuracy guarantee is
  unchanged for claims about the contract, because those are what the quote verification checks.
  Cost: the explanation is the model's own knowledge and is not verified. It is labelled for that
  reason, and is left out of simple lookups.

Temperatures:
  Fixed values are replaced by one setting per stage: plan 0.3 (varied search wording helps the
  refine step avoid repeating itself), judge 0.1 (grading should be steady), answer 0.4 (natural
  explanations). Some models reject any temperature but their default; that error is detected, the
  call is retried without a temperature, and the result is remembered so it happens once.
  The search index format changed, so existing indexes are discarded on startup and rebuilt on each
  document's next question. Documents and conversations are untouched.


D15. Citation highlighting on the real rendered page
----------------------------------------------------
The brief points out that extracted text and the rendered page are laid out differently. Showing the
highlight only in the extracted-text view would sidestep exactly that problem, so the original file
is rendered and the highlight is drawn on it.

Rendering: PDFs are drawn with pdf.js (a canvas for the look, a transparent text layer for the
words). DOCX files are drawn with docx-preview. The original upload is served by
GET /api/documents/{id}/file, inline, with range support so large PDFs load progressively. Only
pages near the viewport are drawn and the rest are released, so a 150-page contract stays light.
The extracted-text view remains as a second tab and as the fallback if a file cannot be rendered
(password-protected, damaged).

Mapping: the server's character offsets describe ITS extraction, and a viewer breaks the same words
into different pieces and sometimes a different order. So offsets are not carried across. Instead
the viewer takes the verified quote text and finds it again in the text it rendered:
  - the match ignores all whitespace, case, curly quotes, dashes, ligatures and soft hyphens, so
    line breaks and the missing spaces between pdf.js text spans do not matter;
  - a second pass ignores hyphens, for words split at the end of a line;
  - if the full quote is still not found (for example a table the viewer read in another order),
    the start and end of the quote are found separately and the stretch between them is used, but
    only if that stretch is a plausible length;
  - if none of that works the interface says so plainly and offers the extracted text instead of
    drawing a highlight in the wrong place.
The matched span becomes real on-screen rectangles through the browser's own Range geometry, merged
per line, so a quote that wraps over three lines is three clean bars.

Quotes that span a page break: the server returns one range per page. Each part is located on its
own page, and the viewer centres the whole span when it fits on screen, so both halves are visible.

Quotes that appear more than once: the server now returns EVERY occurrence in document order and
marks the one on the page the model cited as primary. Which repeat on a page is meant is decided by
counting identical occurrences before it in the server's text and taking the same-numbered one in
the rendered text. The interface shows "2 of 3" with previous and next buttons that wrap around.

Why not highlight by offset into the text layer: pdf.js's text order and the extractor's order
differ for tables, columns and headers, so offsets would drift and highlight the wrong words
without any sign of trouble. Finding the words again fails loudly instead.

Verified in a real browser against a rendered PDF and DOCX, covering: a quote wrapping over several
lines, a sentence crossing a page break, a clause repeated on three pages, an unverified quote that
must not be openable, zoom, and the DOCX view (30 checks).

Known limits: scanned pages have no text, so nothing on them can be quoted or highlighted. Quotes
inside images are not found. A DOCX is shown as docx-preview renders it, which is close to but not
identical to Word. DOCX fit-to-width uses CSS zoom (Chrome, Edge, Safari, Firefox 126 and later).
pdf.js's legacy build is used because the current build needs very new browser features and failed
outright on Chrome 138.



D16. Questions across several documents
---------------------------------------
Requirement: select several documents and ask one question; each quote says which document it came
from; the answer compares rather than listing separate answers; each quote is verified against its
own document, not the whole set.

Conversations replace "chat per document". Chat history used to hang directly off a document. A
question across documents has no single owner, so messages now belong to a CONVERSATION, which has an
ordered list of documents. A one-document chat is simply a conversation with one document (created
the first time it is needed), so the existing endpoints and behaviour are unchanged. Existing saved
chats were migrated to one-document conversations on upgrade, history intact. Deleting a document
removes only the conversations that are left with no documents; a comparison that still has other
documents keeps its history, and quotes from the deleted document say it was deleted.

Retrieval is per document, not pooled. Pooling every chunk into one ranking lets a long contract
crowd a short one out of the top results, and a comparison needs evidence from each. Each document is
searched and ranked on its own and contributes up to CANDIDATES_PER_DOCUMENT passages per round
(shrunk automatically so the judging call stays small when more documents are chosen). Up to
MAX_DOCUMENTS_PER_QUESTION (default 5) documents can be compared.

Sufficiency is judged per document. One judging call sees every document's passages grouped under
its label (D1, D2, ...) and says, for each, whether that document's own passages answer the question.
A document is never marked sufficient because ANOTHER document answered. Later rounds search only
the documents that are still short, using what each one was missing. Documents that never produce
anything relevant are reported plainly ("no relevant passage was found in D2"), as a result of
searching and not as proof of absence, and the evidence panel shows each document as strong,
partial, or nothing found. If no document has anything, no answer is generated, as with one document.

The answer compares. The prompt asks for ONE integrated comparison that leads with the headline
difference or similarity and goes point by point, and forbids a separate summary per document unless
there is nothing to compare. The general-explanation section works as before.

Attribution is checked by code, per quote. Every quote names a document and an evidence passage.
The document is taken from the evidence passage. The quote is then searched for in THAT document's
text only. Consequences that are tested: a sentence that exists in document A but is credited to
document B fails; a quote whose named document disagrees with its evidence passage fails; a quote
naming an unknown document fails; identical wording in two documents is verified separately in each
and produces two citations. Without this, checking against the combined text would let a misattributed
quote pass, which is exactly the failure a comparison is most likely to produce.

Interface: select documents with checkboxes in the library (the order chosen is the order shown),
choose Compare, and a comparison page opens with the chat on one side and a tab per document on the
other. Opening a quote switches to the right document and highlights it on the rendered page, using
the same viewer as a single document. Saved comparisons are listed on the home page and reopen with
their history.

Trade-offs: a comparison costs more model time than a single question (one extra judging stage and a
longer answer prompt), and the cap of five documents keeps it bounded. The single-document loop was
left untouched and the comparison loop is a separate module that reuses its helpers, so the
well-tested single-document path could not regress. The cost is some duplicated loop structure.


D17. Comparing two versions of a contract
-----------------------------------------
Requirement: take two versions, report differences at clause or paragraph level (not a character
diff), explain in plain language what changed in substance, and let the reader filter or sort by how
much a change matters. A liability cap going from AED 100,000 to AED 1,000,000 must never be treated
as a rewording.

Pipeline: segment -> align -> diff each pair -> rate -> overview. Each stage is a separate module
with its own tests, and only the rating and the overview use a model.

1. Segmentation by code. Each version is split into clauses at numbering ("12.", "12.1", "(a)") and
   headings. Running headers, footers and page numbers are removed, and a clause that continues across
   a page break is joined, so the same clause is not reported twice because of a layout change. A
   heading with no body is dropped rather than reported as a clause.

2. Alignment by code, not by the model. Clauses are matched first by identical text ignoring their
   number, then by TF-IDF cosine similarity (0.5, or 0.7 for short clauses, with a bonus for the same
   heading), then by position between already-matched neighbours when the wording overlaps enough. A
   longest-increasing-subsequence pass marks clauses that kept their wording but changed place as
   "moved", which is shown without any wording change. Matching on content instead of clause number is
   deliberate: inserting clause 4 renumbers everything after it, and a number-based match would report
   the whole rest of the contract as changed.

3. Substance is checked by code first. Regular expressions extract money, percentages, durations,
   dates and obligation words (shall/may/must, not, at least) from both sides and compare them. A
   changed figure or obligation word gives the change a floor: figures at least "major", obligation
   words at least "minor". A model cannot talk its way below that floor, and that was observed
   during testing, where the scripted model called a 30 to 45 day payment term cosmetic and the
   floor raised it to major. The card says when this happened.

4. The model rates the rest. Changes are rated in batches, concurrently, as critical / major / minor /
   cosmetic with a category, a short title and a one-sentence summary. The prompt says outright that
   a reworded sentence is not a changed figure. The final rating is the HIGHER of the model's and the
   floor from step 3, so the code can only make the result more cautious.

5. Without a model the feature still works. Figure and obligation changes keep their floors, and
   additions and removals are marked "Not rated" rather than guessed, with a banner saying that
   ratings are rules-only. A change that is pure formatting, numbering or a thousands separator is
   cosmetic with no model. "Not rated" sorts above "minor", because a person has to look at it.

6. The display diff is of the clause body only, at word level, and the heading is shown separately.
   A clause that became number 5 instead of 4 is not shown as a change. Differences in punctuation
   or case only are not reported at all.

7. Runs as a background job with stage and progress, stored with the result so it reopens instantly.
   Asking for the same ordered pair again reuses the stored result. A comparison interrupted by a
   restart is marked failed on startup instead of staying "processing" forever.

Interface: select exactly two documents and choose "See what changed" (the first selected is the
older). The overview leads with the headline and key points that quote the exact figures, marked as
written by AI; changes are listed most significant first, filterable by significance, type and
category, and sortable by significance, document order or category. Each change shows before and
after side by side with the changed words struck out and added, and opens the clause in either
original document with the same highlighting viewer as the chat.

Trade-offs and limits: the model rates at most MAX_AI_RATED_CHANGES changes, and any beyond that
are left to the rules. Clause detection is heuristic, so a contract with unusual numbering may be
split coarsely, which makes a change cover a larger block. Scanned documents with no text layer
cannot be compared. Not yet run against a real OpenAI key: the prompts were exercised with a
scripted model, so the model's actual rating quality is unverified.


D18. Part C: agentic document research (Option 2)
-------------------------------------------------
Choice: Option 2 over Option 1 (tracked-change redlining). Option 2 builds directly on the agent, the
quote verifier and the streaming interface that already exist, so the effort goes into the hard part
of the brief (a loop that stays bounded and survives bad model output) and not into OOXML plumbing.
Option 1 is a different skill (editing Word XML runs without disturbing formatting) and would have
been a worse use of the remaining time. Not attempted, so nothing about it is claimed.

What it is: a second way of answering, chosen with a Standard / Research switch beside the question
box (single document only). In Research mode the model is given three tools and decides for itself
what to look up before anything is answered:
  search_document(query, max_results)   hybrid keyword + embedding search, returns passages
  get_section(number)                   one clause in full with its sub-clauses; a heading also works
  list_clauses()                        the contract's table of contents with pages
A real loop: the model calls tools, reads the results, and calls more, for example following "subject
to clause 14" with get_section("14"). Standard mode is unchanged and remains the default, because it
grades what it retrieved and is cheaper and more predictable. Research mode trades cost and speed for
flexibility, and the interface says so.

Shown as it happens: every call is announced before it runs ("Searching for "termination notice"",
"Reading section 12") and its outcome after ("Found 5 passages on pages 4, 5"), with "Deciding what to
look up next" between calls. These are the same events the saved history keeps, so a past answer can
be expanded to show what was looked up.

Hard limits, enforced in code and not requested of the model:
  - MAX_RESEARCH_ROUNDS (6): the loop ends at the cap whatever the model wants. The answer is then
    written from what was read and marked partial, and the interface says a limit was reached.
  - MAX_TOOL_CALLS_PER_ROUND (4): extra calls in one turn are not run. Each still gets a reply,
    because the provider rejects the next request if any tool call is left unanswered.
  - MAX_INVALID_TOOL_CALLS (4): a model that keeps sending bad calls is stopped.
  - Results are size-capped (passage and section length), and evidence kept for the answer is capped.
  - An identical repeated call is not run again; the model is told it already has that result.
Together these bound the number of model calls per question (at most rounds + 1 answer call).

Malformed or invented calls never crash the request. Every call goes through one function that
returns a message instead of raising. Handled and tested: a tool name that does not exist (including
an empty name), arguments that are not valid JSON, arguments that are not an object, a missing
required argument, a wrong type, an out-of-range value, and extra unknown arguments (rejected, not
silently ignored). The model receives a plain description of what was wrong plus an example of a
correct call, so it can correct itself on the next turn, and the interface shows the correction
happening. Calls that fail count against the invalid-call budget above.

If the model never uses a tool (answers from memory), it is asked once to look things up, and if it
still does not, the question is searched once with the user's own words. The user therefore never gets
an answer that was not read from the document. A greeting or off-topic message is declined without
searching.

Verified quotes still apply, with the same verifier as Standard mode. The answer is written in a
separate step from only the passages the model actually read (numbered E1, E2, ... as they were shown
to it), streamed, and every quote is searched for in the document text by code. A quote that is not
there is shown as unverified. The model never writes the answer inside the tool loop, so tool results
cannot leak into the answer unchecked.

Quality has no separate grader in this mode. It comes from the check: all quotes verified and no
limit hit is "strong evidence"; otherwise "partial". Coverage shows lookups and rounds instead of
search rounds.

Not supported, deliberately: research across several documents (the tools would need a document
argument and the attribution checks of D16 would have to be repeated for it); the API rejects the
combination instead of quietly falling back. The chosen mode is remembered per browser.

Limits: the tool-calling path of the real OpenAI client is covered by tests with the SDK stubbed, but
it has not been run against a live key, so how well a real small model chooses tools is unverified.
Models that ignore tool_choice or return arguments in odd shapes are handled by the checks above, at
the cost of extra rounds.
